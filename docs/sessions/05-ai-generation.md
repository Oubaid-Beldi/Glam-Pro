# Session 5 — AI post generation

**Date:** 2026-08-16
**Live URL:** https://glampro.netlify.app/

## What was built

- `netlify/functions/generate-posts.ts` — a new Netlify Function (Express + `serverless-http`, same pattern as `api.ts`), routed at `POST /api/generate-posts` via a dedicated `netlify.toml` redirect (added *above* the existing catch-all `/api/*` redirect, since that catch-all only ever pointed at the `api` function — see deviations below):
  - Requires a Supabase `Authorization: Bearer <access_token>` header; validates it server-side with `supabase.auth.getUser(token)` using a plain client built from `SUPABASE_URL`/`SUPABASE_ANON_KEY`.
  - Takes `{ projectId, objective }`. Looks up the project by ID using a **second** Supabase client scoped with the user's JWT as its `Authorization` header, so the existing `projects` RLS policy (owner-only) both fetches the project name for the prompt *and* doubles as the authorization check — a caller can't generate posts for a project they don't own, for free, with no extra code.
  - Calls Groq's OpenAI-compatible chat completions endpoint directly via `fetch` (no `openai` npm package — Groq's API already matches the OpenAI request/response shape, so a raw `fetch` avoids an extra dependency for a single call site). **Model: `llama-3.3-70b-versatile`.** `response_format: { type: 'json_object' }` (Groq's JSON mode) plus `temperature: 0.8`. A 20s `AbortController` timeout wraps the call.
  - **Prompt template** (worth preserving verbatim for future tuning):
    - System: *"You are a LinkedIn content strategist writing on behalf of a project team. Write concise, engaging LinkedIn post drafts (roughly 80-200 words each, no hashtag spam, no emoji overload). Respond with ONLY valid JSON matching this exact schema, no markdown fences, no commentary: {"drafts": string[]} "drafts" must contain between 1 and 3 items."*
    - User: `Project: ${projectName}\nObjective: ${objective}\n\nWrite 1 to 3 distinct LinkedIn post draft variants for this project and objective.`
  - Response parsing: `JSON.parse(content).drafts`, validated as a non-empty string array (truncated to 3 if the model over-produces), with a distinct error for every failure mode — missing/invalid auth (401), project not found/not owned (404), bad request body (400), Groq unreachable/timeout (502/504), Groq rate-limited (429 passthrough), empty/non-JSON/malformed model output (502) — none of them crash the function or return an opaque 500.
- `src/lib/use-posts.ts` — `usePosts(projectId)` plain hook (same reasoning as `use-tasks.ts`/`use-notes.ts`), lists the project's `posts` and exposes `createPost` (inserts with `status: 'draft'`, storing the full `ai_variants` array alongside the single edited `content` that was validated).
- `src/pages/Marketing.tsx`: objective form → "Generate" (calls the function with the signed-in user's `session.access_token`) → each of the 1-3 returned drafts renders in its own editable `Textarea` with a per-draft "Validate" button → validating saves that one edited draft as a new `posts` row via `createPost` (client-side `supabase.from('posts').insert(...)`, same RLS-scoped pattern as Tasks/Notes — no need to route the save through a function) and marks that draft "Saved" (disabled, badge). A "saved posts" list below shows the project's existing draft posts (objective, status badge, content, date) — read-only this session, no edit/delete/scheduling yet (that's session 6 per the plan).
- No schema or RLS changes — session 1's `posts` table and its `owner_id`-chained policy already covered everything this session needed.

## Decisions / deviations from CLAUDE.md and the plan

- **`netlify.toml` needed a new redirect.** The existing `/api/* -> /.netlify/functions/api/:splat` catch-all only ever routes to the `api` function, regardless of path — it was never going to reach a second function. Added `/api/generate-posts -> /.netlify/functions/generate-posts` *above* the catch-all (redirect order matters, first match wins). Any future function beyond `api.ts` will need the same treatment.
- **No `openai` npm package.** Used a raw `fetch` to `https://api.groq.com/openai/v1/chat/completions` instead. CLAUDE.md's "OpenAI-compatible client" describes Groq's API shape, not a mandate to pull in the SDK — a single call site didn't justify the extra dependency.
- **Two Supabase clients in the function, not one.** First attempt used a single client constructed with a global `Authorization: Bearer <token>` header for both `auth.getUser(token)` and the RLS-scoped `projects` query. This **broke `getUser` in production** in a way that looked like an auth bug but wasn't (see the big one below) — after fixing the real root cause it still felt fragile to double-purpose one client for both roles, so it's now a plain `authClient` (anon key only) for `getUser`, and a separate `userClient` (anon key + user JWT header) for the RLS-scoped project lookup. Matches Supabase's documented server-side JWT-verification pattern more directly.
- **Major bug found and fixed: production's `SUPABASE_URL` was never actually corrected.** Session 1's log claims the URL was normalized from a user-provided value that included a `/rest/v1/` suffix down to the bare project host before it went into Netlify. It wasn't — the live `SUPABASE_URL` env var (production context) still had the `/rest/v1/` suffix, and had for four sessions. Nothing caught it until now because `api.ts`'s only route (`/health`) never touches Supabase — this was the first server-side code in the whole project to actually call it. The suffix made `supabase-js` build malformed double-path URLs internally (e.g. `.../rest/v1//auth/v1/user`), which surfaced as `getUser()` failing with "Invalid path specified in request URL" — this presented to users as a generic "Invalid or expired session." error on every single generate attempt, authenticated or not.
  - **Found via:** a temporary, deliberately-scoped diagnostic (`detail: userError?.message` added to the 401 JSON response, removed again once the root cause was confirmed and fixed — never a debug endpoint or a permanent behavior change).
  - **Confirmed independently by the user**, hitting the same error on a completely fresh Google sign-in in their own browser (screenshot showed a different project, "Porject 1", ruling out a stale-session explanation).
  - **Fixed with explicit user sign-off** (this touches live infra config, so it was proposed and confirmed before running): `netlify env:set SUPABASE_URL "https://ihgfkcnorylegchoddxx.supabase.co" --context production`, matching the already-correct `VITE_SUPABASE_URL` value (no guessing — the correct value was already sitting in `.env.local`). Also corrected the `dev` context copy for future local `netlify dev` sessions (same stale suffix, lower stakes, no user confirmation needed for a local-only value). Redeployed via `netlify deploy --build --prod` since env var changes don't retroactively apply to an already-built deploy.
  - **Also learned:** `netlify env:get` masks any var Netlify has flagged as containing a secret (`GROQ_API_KEY`, `SUPABASE_ANON_KEY`) — it returns something like `****************861d`, by design, not a bug. Non-secret vars like `SUPABASE_URL` return their real value. This is why a local `.env` seeded from `netlify env:get` for `netlify dev` testing didn't work for the secret-scoped vars and had to be abandoned in favor of testing the Groq call in isolation with a raw `fetch` script instead.
- **Verification workaround for the auth wall, extended this session:** rather than a debug harness mocking Supabase (session 4's pattern doesn't apply well here — the whole point was verifying the *real* server-side auth check and the *real* Groq call), used `netlify dev` locally to catch the redirect-routing and env-var-presence issues cheaply, then relied on a real, already-authenticated Playwright browser session against the *live* site for the actual full round-trip — this is what surfaced the `SUPABASE_URL` bug in the first place, and per the user's explicit request this session, the round-trip was completed for real (not just locally): live "Generate" → 3 real Groq-authored drafts → edit → "Validate" → confirmed as a real row in the `posts` table, persisting across a page reload.
