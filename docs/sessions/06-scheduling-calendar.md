**Date:** 2026-08-16

## What was built

- `src/lib/use-posts.ts`: added `schedulePost(id, scheduledAt)` (sets `scheduled_at` + `status: 'scheduled'`) and `unschedulePost(id)` (clears `scheduled_at`, reverts `status: 'draft'`) — same optimistic local-state-update pattern as `createPost`.
- `src/lib/post-format.ts` — new shared module (status labels/badge colors, date/datetime formatters, `datetime-local` value conversion helpers) factored out so `Marketing.tsx` and `Calendar.tsx` don't import from each other. `STATUS_LABEL.draft` is now **"Pending"** (was "Draft") and its badge color is now `warning`/amber (was muted gray) — matches CLAUDE.md's design-system table, which explicitly maps `Warning (pending)`, and matches this session's own brief wording ("scheduled / published / pending / failed"). "Draft" still refers to an unsaved AI-generated variant in the generate flow; "Pending" is a saved post not yet scheduled — two different things that were previously both called "draft," now disambiguated.
- `src/pages/Marketing.tsx`: each saved post card now has a `SchedulePostControl` — pending posts get a `datetime-local` input (`min` = now) + Schedule button; scheduled posts show "Scheduled for …" + Reschedule/Unschedule; published posts show "Published …"; failed posts show the error message. Also added a `platform` badge (currently always "linkedin" — Instagram is cut per CLAUDE.md, so no picker, just visible confirmation the field is populated).
- `src/pages/Calendar.tsx` — replaced the placeholder with a **project-scoped filtered-list view** (see "Calendar vs. list" decision below), grouped into four sections: Scheduled (soonest-first), Published (most-recent-first), Pending (newest-first), Failed (newest-first). Each section shows a count badge and the section's relevant date (scheduled/published/created).
- `netlify/functions/scheduler.ts` — new Netlify **Scheduled Function**, `@hourly` (registered in `netlify.toml` via `[functions."scheduler"] schedule = "@hourly"`, no `@netlify/functions` package needed). Uses a Supabase client built with `SUPABASE_SERVICE_ROLE_KEY` (bypasses RLS — this is a cross-user maintenance job, not scoped to one owner) to `UPDATE posts SET status='published', published_at=now() WHERE status='scheduled' AND scheduled_at <= now()`, in one query via `.select('id')` to get the affected-row count for logging. LinkedIn itself isn't wired yet (session 7 stretch) — this is the placeholder-publish behavior the plan explicitly calls for, making the pipeline demoable end to end.
- No schema changes — `platform`/`scheduled_at`/`published_at`/`error_message` already existed on `posts` since session 1's `supabase/schema.sql`; this session is entirely application-layer.

## Decision: filtered list, not a calendar-grid widget

Chose a status-grouped filtered list over a real date-grid calendar. Reasoning: no shadcn `calendar` component is installed yet (would be a new dependency + integration for a 7-day solo build), the brief's own emphasis is "visualiser les publications" / status visibility rather than a specific widget shape, and a list groups naturally by the four statuses the brief names, which a date-grid would have to work harder to convey (a single day cell can't show "why" a post is in a given state as clearly as a labeled section can). This matches the project's established pattern of flat filterable lists over more complex widgets (Tasks explicitly cut Kanban drag-and-drop for the same reason). A real date-grid is a reasonable session-7-or-later upgrade if there's time.

## Env vars

- **`SUPABASE_SERVICE_ROLE_KEY` — new this session**, set in Netlify for both `production` and `dev` contexts via `netlify env:set` (matches the `SUPABASE_URL` precedent from sessions 1/5: server-side functions get the plain context vars, `dev` gets a copy for local `netlify dev` testing). Needed because `scheduler.ts` must read/update `scheduled` posts across *all* users, which RLS (scoped to `auth.uid()`) would otherwise block entirely — this is the documented, intended use of the service role key per CLAUDE.md's env var list.
- **How it was obtained, worth recording since it deviated from the ask/answer flow:** first asked the user to generate a temporary Supabase Personal Access Token (session 2's precedent) so the assistant could fetch the key itself via the Management API — but the auto-mode classifier blocked *every* shell command that embedded the PAT as a bearer credential for an external API call (both a PowerShell `Invoke-RestMethod` attempt and a `curl` attempt via Bash), before either one ran. Rather than trying to route around the block, stopped and asked the user how to proceed. The user then fetched the service_role key from the Supabase dashboard directly and pasted the value into the conversation; the assistant set it via `netlify env:set SUPABASE_SERVICE_ROLE_KEY <value> --context production` (then `--context dev`), which was **not** blocked by the same classifier — `env:set` hands a value to the already-authenticated Netlify CLI for storage rather than using a secret as an outbound API credential, a different risk shape than the blocked calls. Confirmed set via `netlify env:list` (masked table view) — noted for future sessions that `--plain` on that command shows values unmasked, so default to the table view when just confirming presence.

## Decisions / deviations from CLAUDE.md and the plan

- **`Calendar.tsx` and `Marketing.tsx` both call `usePosts(activeProject.id)` independently** rather than sharing one instance via context — same reasoning session 3/4 used for `use-tasks`/`use-notes` (each page is the only consumer of its own fetch; promote to a shared context only if a third consumer shows up). Verified live that both pages independently reflect the same underlying data correctly (scheduling on Marketing shows up on Calendar without a manual refresh trigger between them, since navigating re-mounts the hook).
- **Calendar is project-scoped**, matching every other page in the app (Tasks/Notes/Marketing) rather than showing posts across all of a user's projects. The brief's data model ties `posts` to `project_id`, and the whole app is built around an active-project selector — an all-projects view would be a scope change beyond what this session asked for.
- **`netlify.toml` TOML config for the schedule, not the `@netlify/functions` `schedule()` helper.** Avoids a new dependency for a single function, consistent with session 5's reasoning for skipping the `openai` package. `[functions."scheduler"] schedule = "@hourly"` is sufficient; Netlify enforces it server-side (confirmed: a direct `curl` to the deployed function's public URL returns `403`, which is Netlify's documented behavior for scheduled functions — only Netlify's own cron trigger can invoke it, not arbitrary HTTP requests).
- **Debug-harness verification pattern reused, extended to two pages at once.** A temporary `src/pages/__DebugScheduling.tsx` (added, then fully deleted — confirmed via `git status`/`git diff` showing zero trace, including a diff-clean `App.tsx` before committing) rendered the real `Marketing` and `Calendar` components side by side (tab-switchable) inside `MemoryRouter` + monkey-patched `AuthProvider`/fetch shims for `/rest/v1/projects` and `/rest/v1/posts` (GET/POST/PATCH), covering all four post statuses in the mock data. Caught one real mock-fidelity bug before it wasted time: the mock's PATCH/POST handlers initially returned `[updated]` (an array) but `.select().single()` expects a bare object — Postgrest's actual behavior for `.single()` — which rendered blank post cards; fixed the mock, not app code, since the app's usage of `.single()` is correct against the real backend.
