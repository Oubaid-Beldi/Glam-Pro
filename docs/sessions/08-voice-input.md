# Session 8 — Voice input

**Date:** 2026-08-30
**Live URL:** https://glampro.netlify.app/

## What was built

Speak-the-objective flow for AI post generation, on top of session 7's layering — no new provider, no new env var, same `GROQ_API_KEY` already used for chat completions.

- `server/integrations/groq.client.ts` — added `transcribeAudio(apiKey, audioBuffer, mimeType)`. The one and only place that calls Groq's Whisper endpoint. **Model: `whisper-large-v3-turbo`.** Builds a native `FormData`/`Blob` (Node 20's global `fetch`/`FormData`/`Blob`, no new dependency — same "no `openai` npm package" reasoning as session 5/7's chat-completions client) and POSTs to `https://api.groq.com/openai/v1/audio/transcriptions`. Reuses the existing `GroqCallError`/timeout-via-`AbortController` pattern from `callGroq`, 20s timeout. Returns `{ ok: true, transcript }` or a typed error, never throws.
- `server/services/voice.service.ts` — `transcribeObjectiveAudio({ token, audio, mimeType })`: framework-agnostic, verifies the Supabase bearer token via `createAuthClient(...).auth.getUser(token)` (same auth-only pattern `posts.service.ts` uses, reused rather than duplicated — this endpoint isn't project-scoped so there's no RLS-scoped lookup needed, just proof the caller is a real signed-in user, so the shared Groq quota isn't open to anonymous callers), rejects empty/oversized audio (15MB cap, generous headroom above a 60s recording), calls the integration, maps every failure kind to a typed result + message. Discriminated-union result type, no thrown exceptions — same shape as `posts.service.ts`/`scheduler.service.ts`.
- `server/controllers/voice.controller.ts` — thin: pulls the bearer token and `{ audioBase64, mimeType }` off the request, `Buffer.from(audioBase64, 'base64')`, calls the service, maps its result status to an HTTP code (`ok`→200, `config_error`→500, `unauthorized`→401, `bad_request`→400, `timeout`→504, `provider_unreachable`→502, `rate_limited`→429, `bad_response`→502). No business logic, no direct Groq/Supabase calls.
- `server/routes/voice.routes.ts` — `POST /posts/transcribe`, mounted under `/api` in `netlify/functions/api.ts` (so the live path is `POST /api/posts/transcribe`), alongside the existing health/posts routers. No new Netlify Function, no new `netlify.toml` redirect — same generic `/api/*` catch-all covers it.
- `server/types/voice.types.ts` — `TranscribeRequestBody { audioBase64, mimeType }`, `TranscribeResponseBody { transcript }`, following `posts.types.ts`'s pattern.
- `netlify/functions/api.ts` — bumped `express.json()`'s body limit from Express's 100kb default to `10mb`. A base64-encoded 60s webm/opus recording runs well past 100kb (opus at typical browser defaults is roughly 0.5–1.3MB before base64's ~33% overhead), so the default limit would have rejected a full-length recording outright.
- `src/lib/use-voice-transcription.ts` — new hook, `useVoiceTranscription(accessToken, onTranscript)`. Owns the whole client-side lifecycle:
  - `start()`: `getUserMedia({ audio: true })` → `MediaRecorder` (`audio/webm` if supported, browser default otherwise) → `state: 'recording'`, a 250ms interval tracks elapsed seconds and calls `stop()` automatically at the **60-second cap**.
  - `stop()`: stops the recorder; `onstop` releases the mic stream, and if the recording ran under **1 second**, treats it as an accidental tap (`"Recording was too short..."` error, nothing sent to the server) rather than sending a near-empty clip.
  - `cancel()`: settable at any point *while* recording (a `cancelledRef` flag checked in `onstop`) — stops the recorder/mic without ever calling the transcribe endpoint. This is the "cancel a recording before sending it" requirement: cancel is available for the whole span between starting and the recording being sent, not a separate post-stop confirmation step.
  - On a valid stop, blob → base64 (`FileReader.readAsDataURL`, stripped to the base64 payload) → `POST /api/posts/transcribe` with the session's `access_token` → on success, calls `onTranscript(transcript)`; on any failure (missing session, non-2xx response, network error, empty transcript) sets a visible `error` string and returns to `idle`. Every failure path is user-visible, nothing fails silently.
- `src/pages/Marketing.tsx` — `VoiceRecorderControl` renders next to the "Objective" label: idle → mic icon button; recording → pulsing (`animate-pulse`) red stop button + `"Recording… Ns / 60s"` + a Cancel button; transcribing → spinner + `"Transcribing…"`. `onTranscript` is wired directly to `setObjective`, so a finished transcription **fills** the existing objective `Textarea` — it does not touch `drafts`/`generating` state or auto-submit. The user sees the transcribed text in the same editable field they'd have typed into, and presses the existing "Generate" button themselves.

## Recording length cap and model, for future tuning

- **Cap: 60 seconds**, enforced client-side only (`MAX_SECONDS` in `use-voice-transcription.ts`), via the interval timer calling `stop()` once elapsed time reaches it. The server independently caps at 15MB regardless of duration, as a backstop, not a duration check.
- **Minimum: 1 second** (`MIN_RECORDING_MS`), also client-side, to reject accidental single-click taps before they're even sent.
- **Model: `whisper-large-v3-turbo`** — Groq's fastest/cheapest Whisper tier, chosen because this is a short-form single-field dictation UX (an "objective," not a long-form transcript), where latency matters more than maximum accuracy. If transcription quality on accented speech or background noise turns out to be a problem in practice, the largest option on Groq's catalog is `whisper-large-v3` — a one-constant change in `GROQ_TRANSCRIBE_MODEL` in `server/integrations/groq.client.ts`, same pattern as session 7's `GROQ_MODEL` swap.

## Decisions / deviations from the brief

- **The brief's illustrative code described calling `audio.transcriptions.create()` via "the same OpenAI-compatible client already used for chat completions."** There is no `openai` SDK client instance in this codebase — session 5/7 already established raw `fetch` over the `openai` npm package for the chat-completions call, specifically to avoid the dependency for a single call site. Extended that same reasoning here: `transcribeAudio` is a raw `fetch` to Groq's `/audio/transcriptions` endpoint using Node's global `FormData`/`Blob` (available since Node 18, no new dependency), not an SDK call. The *account and API surface* are exactly what was asked for — Groq's OpenAI-compatible Whisper endpoint, same key — just not literally through an `openai` package import, consistent with the rest of `groq.client.ts`.
- **`/api/posts/transcribe` requires the same `Authorization: Bearer <token>` + Supabase `getUser()` check as `/api/generate-posts`,** even though the brief didn't explicitly say the transcribe endpoint needs auth. Added it because the endpoint would otherwise be a public, unauthenticated way to spend the shared Groq quota — the same reasoning that led `generate-posts` to require auth in session 5. No RLS-scoped project lookup is needed here (transcription isn't tied to a project), so the service only does the `authClient.auth.getUser(token)` half of `posts.service.ts`'s two-client pattern, not the `userClient` half.
- **Cancel is available only while recording is in progress, not as a separate "review before send" step after stopping.** The brief's "let me cancel a recording before sending it" was read as: don't let a recording get sent without an opt-out. Stopping (clicking the mic button again) both ends the recording *and* immediately sends it for transcription — there's a distinct Cancel action available the whole time recording is live, but no extra confirmation step between stop and send. Simpler state machine, still satisfies the requirement as written.
