# Session 9 — LinkedIn auto-publish + polish

**Date:** 2026-09-06
**Live URL:** https://glampro.netlify.app/
**Outcome: primary goal shipped.** LinkedIn OAuth connect + auto-publish is live and confirmed working end to end (real scheduled function, real LinkedIn post). The manual fallback (Copy content / Mark as published) also shipped alongside it, not instead of it — kept as a resilience layer since the live connection depends on a token that expires after ~60 days with no refresh.

## What was built

Following session 7's layering throughout — no flat files added to `netlify/functions/`.

- **`server/integrations/linkedin.client.ts`** — the only place that calls LinkedIn's API directly: `buildAuthorizationUrl()` (pure), `exchangeCodeForToken()` (POST `/oauth/v2/accessToken`), `fetchMemberUrn()` (GET `/v2/userinfo`, OpenID Connect), `publishPost()` (POST `/v2/ugcPosts`, UGC Posts API). Same typed-result-never-throws pattern as `groq.client.ts`.
- **`server/services/linkedin.service.ts`** — `startLinkedInConnect()`, `handleLinkedInCallback()`, `getLinkedInStatus()`, `publishToLinkedIn()`. Owns the OAuth "state" signing: HMAC-SHA256 over `{uid, ts}` using `LINKEDIN_CLIENT_SECRET` as the signing key (no new env var — it's already a server-only secret dedicated to this integration), verified with `timingSafeEqual` and a 10-minute TTL on callback. This is what lets the connect step (an authenticated fetch, has a bearer token) hand off to the callback step (a top-level LinkedIn redirect, no bearer token) without letting anyone forge another user's `uid`.
- **`server/controllers/linkedin.controller.ts`** + **`server/routes/linkedin.routes.ts`** — `GET /auth/linkedin/connect` (verifies the caller's Supabase token passed as a query param — top-level navigations can't carry an `Authorization` header — then 302s to LinkedIn), `GET /auth/linkedin/callback` (exchanges the code, resolves the member URN, upserts `linkedin_accounts`, 302s back to `/marketing?linkedin=connected|error`), `GET /api/linkedin/status` (authenticated, used by the frontend to show connected/not-connected). `linkedin.routes.ts` defines these as absolute paths and is mounted at the app root in `netlify/functions/api.ts`, since it genuinely serves two different prefixes (`/auth/*` and `/api/*`) — the other route files only ever needed one.
- **`netlify.toml`** — added an `/auth/*` -> `/.netlify/functions/api/:splat` redirect (same generic-rewrite pattern as the existing `/api/*` one), placed before the SPA catch-all.
- **`server/services/scheduler.service.ts`** — `publishDuePosts()` now selects due posts joined with `projects(owner_id)`, and calls `publishToLinkedIn({ ownerId, content })` per post instead of a single bulk status update. `status: 'published'` + `published_at` on success, `status: 'failed'` + `error_message` on any failure (not connected, token expired, LinkedIn API error).
- **`supabase/schema.sql`** — new `linkedin_accounts` table (`owner_id` pk/fk, `access_token`, `member_urn`, `expires_at`), RLS owner-scoped like every other table. Token stored in plaintext — acceptable at this MVP's simplicity level (service-role-only server reads, RLS-scoped). No `refresh_token` column: standard 3-legged LinkedIn OAuth tokens aren't refreshable without a separately-approved "Programmatic Refresh Tokens" product, out of scope here.
- **Frontend** — `src/lib/use-linkedin-connection.ts` (status hook + `connect()` which does `window.location.href = /auth/linkedin/connect?token=...`), a `LinkedInConnectionCard` on `Marketing.tsx` showing Connected/Not connected + a Connect/Reconnect button, and a banner reading the `?linkedin=connected|error` redirect result (cleared from the URL after reading via `useSearchParams`). `src/components/PostActions.tsx` — shared "Copy content" (always) + "Mark as published" (scheduled/failed only) buttons, used on both Marketing's saved-posts list and Calendar's scheduled/failed sections. `use-posts.ts` gained `markPublished()`.
- **Polish** — small spinner icons added next to the "Loading posts…" / "Loading saved posts…" text in Calendar and Marketing (previously plain text, only the voice-transcribing state and the top-level auth loader had a spinner). Nothing else looked broken enough to warrant more than this in the time available — most of this session's time went to the live-debugging incidents below.

## Why publishing lands on the personal profile, not a Company Page

This surprised the user live, worth recording clearly: LinkedIn requires every Developer App to be linked to a Page at **app-creation time**, which reads as "this app is for my Page" — but that link is purely an administrative/ownership anchor, unrelated to what the app is allowed to post *as*. The self-serve "Share on LinkedIn" product only ever grants `w_member_social`, which posts as **the authorizing member** (`urn:li:person:...`), full stop, regardless of which Page the app is linked to. Posting as the Page itself needs a completely separate product, **Community Management API** (`w_organization_social`, author `urn:li:organization:...`), which requires a real LinkedIn review — not something the "Verify company" dialog in the Auth tab unlocks by itself. Decided not to start that review this session (it can't complete today regardless, and the brief explicitly said not to let LinkedIn eat the session) — documented as future work in CLAUDE.md instead.

## Three live-debugging incidents, in order (useful if this integration ever misbehaves again)

1. **`redirect_uri does not match the registered value`** — the very first live attempt. LinkedIn's Auth tab didn't yet have the exact redirect URI (`https://glampro.netlify.app/auth/linkedin/callback`) registered. Fixed by the user adding it exactly (no trailing slash) under "Authorized redirect URLs for your app."
2. **Silent failure, no green "Connected" banner, zero rows in `linkedin_accounts`** — nothing was logged server-side to say why. Added `console.error` at every failure branch in `handleLinkedInCallback()` (state, token exchange, userinfo, DB upsert) and in `exchangeCodeForToken()` (logs LinkedIn's actual response body on a non-ok response, not just our coarse error `kind`). This is what turned an invisible failure into an actionable one — **worth keeping this logging permanently**, not stripping it out as "debug noise," since this is exactly the kind of external-API integration where the next failure years from now will need the same visibility.
3. **`invalid_client: Client authentication failed`** — the real cause, found via the logging above: `LINKEDIN_CLIENT_SECRET` in Netlify held a **truncated** copy of the real secret (LinkedIn's Auth tab displays it in a narrow, visually-truncated text box; selecting the visible text instead of using the copy-icon grabs only part of it — 22 characters instead of the real 33). Confirmed by hashing the value in both Netlify contexts (never printing the raw secret) and comparing lengths before/after the user re-copied it properly using the copy icon.
   - **A fourth, smaller gotcha stacked on top of this one**: after the user corrected the secret in Netlify's dashboard, the *very next* connect attempt still failed with the identical `invalid_client` error. The already-warm Netlify Function container was still holding the old secret value in its process memory — Netlify Functions read env vars at cold-start, not per-request, so a warm container can silently keep serving a stale credential after an env var update. An empty `git commit --allow-empty` + push forced a fresh deploy (and fresh containers), and the very next attempt succeeded. **If an env var is ever updated on a live site and the fix doesn't take effect immediately, trigger a redeploy before assuming the fix itself is wrong.**

## Verification performed

- `npm run typecheck:server`, `npm run build`, `npm run lint` — all clean, same 4 pre-existing lint warnings as sessions 6-8, zero new ones.
- Local `netlify dev`: confirmed `/api/health` → 200, `/api/linkedin/status` (no token) → 401, `/auth/linkedin/connect` (no token) → 302 to `/marketing?linkedin=error`, `/auth/linkedin/callback` (bogus code/state, and `?error=access_denied`) → both 302 to `/marketing?linkedin=error`.

- **Full live round trip, real LinkedIn account**: connected via the actual OAuth consent screen, confirmed a real row landed in `linkedin_accounts` with a resolved `member_urn` and a 60-day `expires_at`. Scheduled a real post; the live `@hourly` Netlify Scheduled Function (not a manual trigger — it fired on its own before a manual trigger was needed) picked it up, called the real LinkedIn UGC Posts API, and flipped the post to `status: 'published'` with `published_at` set and no `error_message`. User visually confirmed the post appeared on their real LinkedIn profile.
- Live post-deploy: polled `/auth/linkedin/connect` until it flipped from the pre-deploy `200` (old deploy, route didn't exist) to `302` (new deploy, route live) — same technique session 8 used for its route-added checks.
